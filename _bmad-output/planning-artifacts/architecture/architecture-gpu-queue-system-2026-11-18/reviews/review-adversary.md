# Architecture adversarial compatibility review

日期：2026-11-18。只读审查 ARCHITECTURE-SPINE.md，未运行业务测试，未修改交付。

结论：同卡唯一分配、旧名额隔离、到期/续期的锁与事务提交顺序形成一致契约。发现一处会让合规实现产生不同队列结果的高优先级问题；应在定稿前收紧 AD-7。另有一处幂等检查顺序可进一步明确。

## High — AD-7 的双锚点不足以决定唯一位置

AD-7 要求被移动项保持与其仍在排相邻锚点的关系，其他项仍按普通规则排序。设 X 被人工移动到 A 与 B 之间，保存锚点 A/B；随后另一个普通项 C 因年龄、审批或新增进入 A 与 B 之间。

- 实现一将 X 紧贴前锚点 A，得到 A、X、C、B。
- 实现二将 X 紧贴后锚点 B，得到 A、C、X、B。

两者都保持 X 在 A 后、B 前，其他普通项 A/C/B 的相互顺序也不变，都满足字面规则，却给出不同的公开队列和获配顺序。更严重的是 A/B 因年龄提升或紧急审批逆序后，同时保持“在 A 后、B 前”可能根本无解。

建议：给出唯一的锁内重建算法，例如先计算普通顺序，按移动事件顺序重放；移除目标后，优先插在仍有效的后锚点之前，后锚点无效才插在前锚点之后，二者都无效回普通位置；明确锚点逆序仍采用同一优先级。或者采用更简单且经用户确认的固定当前队列顺序策略。不要把“查询和分配共用策略”视为已定义了该策略。新增“插入新项、锚点逆序、一个/两个锚点离队、多次移动”的确定输出用例。

## Medium — AD-3 幂等重放应先于当前状态冲突裁决

文本同时要求先验证权限、锁后校验当前名额，以及“同键同载荷返回原结果”，但未明确已提交 command_id 的查找顺序。旧归还已成功、响应丢失、新持有者已获配后重试，若先做旧名额匹配判断会返回失效，若先查已提交命令则返回原成功。

建议：验证当前身份与原命令拥有者后先查已提交命令记录，同指纹直接重放原结果；仅未处理的新命令进入锁和状态判定。同键并发冲突时等待/回滚后读取已提交结果，不把唯一键错误暴露为新的成功或永久失败。不得对陌生操作者泄露原命令结果。

## 未发现上述三类核心风险的其他冲突

- AD-2 固定资源行锁覆盖空闲时无当前名额行的问题，当前映射唯一权威避免历史状态形成另一份占用判断。
- AD-3 独立 allocation_id 与锁后映射匹配能隔离同成员多轮使用权，不能仅凭 GPU 或成员释放。
- AD-4 最新期限重读与成功事务顺序足以区分续期先提交、释放先提交、仅标异常/逾期仍保留三类结果。
- AD-5 同事务副作用和新的转换标识避免一次到期去重吞掉续期后的再次到期通知。

报告不把技术方案视为已验证实现，也不新增用户业务决定。

## 修订复核（2026-11-18）

- High 已关闭：AD-7 现规定先建立基础列表，再按 transition_seq 升序重放移动；后继紧前优先、前驱紧后备选、两者均失效则不移动，明确不维持永久双锚点约束。新增项、锚点逆序和多次移动都有唯一算法结果，原两种合规实现不能继续产生不同顺序。
