# 产品简报：组内 GPU 使用名额排队与分配系统

本简报依据项目负责人与 AI 的真实需求确认编写，已完成简报阶段收尾，可作为 PRD 输入。现状由项目负责人提供，未开展独立访谈或用户验证；系统尚未实现。文末所列细节仍需在 PRD 阶段明确。

## 问题、用户与目标

实验室目前使用纸质申请，高年级优先分配 GPU。项目负责人希望低年级也能获得使用机会，并将申请、排序、使用权分配和归还记录迁移至网页系统。预计服务 30 名成员，管理 10 张 4090。

实验室成员需要申请指定 GPU、查看排队和分配结果、确认开始、申请续期及归还；算力管理员负责紧急申请审核、异常核实、使用权干预与线下交接。第一版的目标是实现可运行、可追溯的名额管理流程，并通过按提交时间排序和随等待时长提高优先级的规则改善分配机会；实际公平性改善尚需使用数据验证。

## 第一版规则

| 环节 | 已确认规则 |
| --- | --- |
| 申请 | 一个名额对应一张指定 GPU。申请时选择卡号，可申请多张、重复排队并同时持有多个名额。普通申请免审批；紧急申请须管理员批准。 |
| 排队 | 普通申请按提交时间排序；等待超过 3 天可排在紧急申请之前。管理员可以手动调序并突破等待保障，因此不承诺绝对最长等待时间。 |
| 分配 | 按卡排队，允许部分分配。甲等待 GPU 2 不阻止乙获得空闲 GPU 3。每张卡从各自分配成功时独立计时。 |
| 使用与续期 | 成员填写预计时长，首次申请最多 3 天；必须点击“开始使用”后再自行登录服务器运行任务。续期须管理员批准，累计使用时长可以超过 3 天。 |
| 异常与到期 | 分配后 24 小时未点击开始，标记异常，管理员核实后释放。已明确的短时例子是：申请 6 小时、到期未确认开始则直接释放。已开始且到期未归还时保留名额并标记逾期，待管理员核实任务完成后释放。 |
| 管理员干预 | 可审批、调序、代为归还、延长时长及撤销使用权；必须填写理由、通知成员并保留操作前后记录。撤销后可以不等待任务完成即重新分配，管理员负责线下通知原成员停止使用并协调交接。 |
| 通知 | 第一版仅采用网页内站内消息；撤销后的线下协调由管理员负责。 |

## 系统边界与主要风险

系统管理使用权和记录。成员自行登录服务器执行训练；第一版不自动执行任务，不接入 SSH 控制、不终止进程、不监测 GPU 实际占用。

“先确认开始再运行”是成员使用约定，系统无法技术上强制。撤销使用权也不会停止任务，因此分配记录唯一不代表实际 GPU 没有运行冲突；管理员承担撤销后的线下交接责任。

主要一致性风险是多个分配操作同时选中同一张卡，或归还、到期释放与管理员撤销并发发生，导致重复有效分配，或误释放新持有者的使用权。后续架构和测试必须验证状态转换及有效分配唯一性，不能只检查页面显示。

## 成功度量与验收方向

- 功能闭环：成员能够完成申请、排队、获得名额、开始确认、续期申请和归还；管理员能够完成审核及异常处理，成员能查看站内通知，干预操作可追溯到理由和前后状态。
- 公平性规则：测试中普通申请不因年级而改变先后；同卡等待超过 3 天的申请排在紧急申请之前，管理员手动干预作为有审计记录的例外。上线后再比较不同年级的等待时长与获得名额情况，不虚构改善比例。
- NFR-候选-1（一致性）：同一空闲 GPU 同时触发 30 次分配尝试，最多产生一条有效分配；重复归还不得重复释放或再次分配。
- NFR-候选-2（权限隔离）：普通成员尝试审批、调序、代归还、直接延期或撤销等管理员操作时均被拒绝，相关业务状态不变；成员仍可提交自己的续期申请。

用户已确认一致性和权限隔离两个方向；上述测试参数及详细用例由 AI 提出，留待 PRD 细化。当前没有实现或测试通过证据。
