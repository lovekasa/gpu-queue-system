# GPU 名额系统史诗划分提案

用户已回复C批准本文件的3个史诗结构与覆盖关系，已写入 epics.md 并进入第3步故事编写。本文件保留第2步提案，不包含故事。后续故事至少12个，具体粒度逐项确认。

## Epic 1：成员安全进入系统并识别指定资源

**用户成果：** 管理员可以建立成员账号，成员登录后可以识别10张指定GPU及名额状态说明；普通成员无法创建账号或越权访问管理员功能。

**FR覆盖：** FR-001、FR-002。角色及本人数据隔离作为后续各功能必须复用的能力。

**实施约束：** 工程初始化纳入首个故事，采用已确认栈和官方create-vue，工程前核实精确版本；只建立本阶段需要的迁移，不一次创建全部未来业务表。Session、同源API、CSRF、受控初始管理员与测试库隔离同时落实。

**可验收边界：** 账号创建、登录和资源识别可独立演示；不以未来申请页面或管理员审核功能作为本史诗的完成依赖。后续操作专属的权限断言随相应操作继续增加，不声称本阶段已经覆盖尚不存在的接口。

## Epic 2：成员完成普通申请、获配、使用与归还闭环

**用户成果：** 成员可提交指定单卡或多卡申请、重复排队，看到本人状态和公共队列，按卡开始和归还；到期状态处理符合规则，异常/逾期可由管理员核实任务完成后释放，站内消息告知结果。

**FR覆盖：** FR-003、004、006、008、009、010、011、017、018；FR-007的普通时间排序、等待提升及同时间顺序；FR-015的获配/异常/逾期/释放消息及已读；FR-016的生命周期记录和核实释放审计。

**实施约束：** 固定GPU行锁、唯一当前映射、独立allocation_id、幂等命令、同事务审计和站内消息从第一个名额写路径开始实现。每项功能同步包含页面、API、持久化和验证，不把事务、权限或证据留到最终“测试史诗”。定时扫描与启动补查完成普通生命周期。管理员核实释放包含理由、审计和通知，不等后续史诗补齐。

**可验收边界：** 使用普通申请即可完整演示等待→部分分配→开始→归还→下一人获配以及异常核实释放；不依赖紧急审批、人工调序或续期。尚未交付的管理入口不暴露；当紧急能力在Epic3加入时复用现有排序策略，不重写普通队列。

## Epic 3：管理员协调紧急需求、续期和例外并保留追溯

**用户成果：** 管理员可以审批紧急申请、调整当前等待项、审核续期、直接延期、代归还和即时撤销；成员能看到处理结果，管理员能查询完整审计并承担线下交接责任。

**FR覆盖：** FR-005、012、013、014；补齐FR-007的紧急组和人工调序、FR-015的全部管理员消息及FR-016完整干预审计与查询。回归FR-001、017、018的权限、本人显示和公共排序。

**实施约束：** 所有干预复用Epic2事务服务，不新增绕过锁的写路径；调序遵循AD-7明确重放规则。续期与到期两种成功提交顺序、旧名额事件、审计/消息失败回滚必须在对应功能内验证。增量补齐可观察性、部署参数及试用前备份恢复演练；课程证据和实验A准备随相关故事记录，不新增实验B。

**可验收边界：** 在已有普通闭环上交付高级协调；没有后续史诗依赖。续期不复活结束名额，撤销不终止训练任务，管理员的线下责任有明确说明。

## 依赖与共享代码检查

顺序为Epic1→Epic2→Epic3，只允许依赖前序已交付能力。Epic1独立完成安全访问和资源识别；Epic2提供普通闭环且包含必要人工核实；Epic3增加例外协调。

Epic2与Epic3会共享名额服务和排序策略。这是普通闭环与管理员例外的风险边界，保留两个用户成果明确的增量；不按数据库/API/前端拆层，不重复建立事务模型。若用户希望合并，需同时讨论课程至少3个史诗的约束，不能通过新增无用户价值的技术史诗凑数。
