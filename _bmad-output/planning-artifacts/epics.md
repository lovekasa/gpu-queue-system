# gpu-queue-system - Epic Breakdown

## Overview

3 个史诗、20 条故事均有已确认的业务范围。按 D047、D048 采用本机 H2 演示和顺序验收。需求沿用 PRD 编号。

## Requirements Inventory

### Functional Requirements

验收条目标识采用 AC-三位 FR 编号-序号，例如 AC-001-1。下列“验收”是将来应执行的检查，不是已完成结果。

### 4.1 身份与资源

**FR-001 身份与角色隔离。** 系统区分成员与算力管理员，账号由管理员创建。

- AC-001-1：成员尝试紧急审批、续期审批、调序、代归还、直接延期或撤销时，操作被拒绝且业务状态不变。
- AC-001-2：成员可发起自己的续期申请，不能把申请操作变成直接延期。
- AC-001-3：管理员可创建成员账号；成员不能自行注册或创建账号、授予管理员权限。
- AC-001-4：成员可查看本人申请、名额和通知；他人在排队列仅公开姓名及顺序，不暴露其申请详情、使用名额详情、通知或完整审计。管理员可查看处理申请及审计所需记录。

**FR-002 指定 GPU 识别。** 提供 10 张 GPU 的独立标识，申请和分配均指向具体卡。

- AC-002-1：申请 GPU 2 获配后，记录显示 GPU 2，不替换成其他卡；资源页面明确描述为名额状态，不宣称实测 GPU 空闲。

### 4.2 申请与排队

**FR-003 普通申请。** 成员可选择一张或多张指定 GPU 并填写首次预计使用时长，普通申请免审批，首次时长最多 3 天。

- AC-003-1：合法普通申请提交后无需管理员审批即可进入等待/分配流程。
- AC-003-2：首次时长仅接受 1–72 的整数小时；1、24、72 小时合法，0、负数、非整数及 73 小时被拒绝。

**FR-004 重复排队与多卡持有。** 允许成员多次排队并同时持有多张不同 GPU。

- AC-004-1：持有 GPU 1 的成员仍可申请 GPU 2；不能仅因已有名额拒绝申请。
- AC-004-2：同一成员重复申请同一卡时，各申请按与其他成员相同的优先级规则正常排队；不得因同一申请人而额外提升或降低优先级，也不得合并或拒绝重复申请。同一卡仍最多一个有效名额。

**FR-005 紧急申请审核。** 紧急申请必须由管理员批准后才获得紧急待遇。

- AC-005-1：未经批准的申请不能按“已批准紧急”优先级参与分配；批准/拒绝须保留理由、通知和审计。
- AC-005-2：紧急审批前按普通申请等待，可按普通规则获配；批准不能重复分配已获配的卡。驳回后继续普通排队，原提交时间不变。

**FR-006 按卡排队与部分分配。** 每张卡独立排队，多卡申请可以分批获得名额，其他卡的等待不阻塞本卡合法分配。

- AC-006-1：甲等待忙碌 GPU 2，乙申请空闲 GPU 3；甲的等待不能阻止乙获得 GPU 3。
- AC-006-2：甲申请 GPU 2、3，只有 GPU 3 可分配且甲在该卡符合顺序时，可先分 GPU 3，GPU 2 保持等待。
- AC-006-3：同一卡按 FR-007 的当前有效排序分配，不得绕过排序在前的等待项；同人重复申请同一卡也适用。

**FR-007 时间顺序与等待提升。** 普通申请按提交时间排序；等待超过 3 天可超过紧急申请；管理员手动调序可突破此保障。

- AC-007-1：无管理员干预和其他优先条件时，普通申请中先提交者先获得该卡。
- AC-007-2：等待从申请提交时起算，恰好 3 天不触发“超过”，超过 3 天可排在紧急申请前；部分获配后其余卡仍沿用原提交时间，不重置等待年龄。
- AC-007-3：无人工调序时，等待超过 72 小时的等待项排在已批准紧急项之前，后者排在其余普通项之前；每组按原提交时间排序。相同提交时间使用系统接收先后固定排序，刷新页面不得改变顺序。
- AC-007-4：管理员调序仅对当前指定等待项有效，不形成成员永久优先级，也不继承到该成员的新申请或其他等待项。当前项获配结束等待后，该项调序不再作用于后续申请。此规则不保证 3 天内获配。

### 4.3 分配、开始与结束

**FR-008 按卡独立计时。** 每张 GPU 从其各自分配成功起计算使用期限。

- AC-008-1：同一多卡申请在 t1、t2 分别获配两张卡，期限分别从 t1、t2 起算，不能统一从申请提交或第一张卡获配时起算。

**FR-009 确认开始与使用约定。** 成员应先在网页确认开始，再自行运行任务。

- AC-009-1：确认开始只更新名额记录；不触发远端任务执行，也不证明成员遵守约定。
- AC-009-2：成员按卡确认开始，开始 GPU 2 不改变同一申请中 GPU 3 的开始状态。违规运行由管理员线下协调，第一版不增加处罚模块。

**FR-010 未开始异常与短时例外。** 分配后24小时未确认开始先标异常，管理员核实后释放；当前已批准期限总跨度不足24小时的名额到期未开始直接释放，跨度定义见§3。

- AC-010-1：当前已批准期限总跨度超过24小时的名额在原分配后满24小时仍未开始，保留名额、标异常，不能直接分给下一人。
- AC-010-2：当前已批准期限总跨度不足24小时的名额到期仍未开始，释放该名额，允许后续分配；至少覆盖6小时及另一种合法短时名额。
- AC-010-3：恰好 24 小时到期且未开始时，先标异常并等待核实，不能直接释放。
- AC-010-4：不足 24 小时的名额，先确认开始再处理到期时，按已开始到期规则保留；先执行到期释放再确认开始时，旧名额仍然结束。分别按两种顺序验收。

**FR-011 归还与逾期处理。** 支持结束使用与归还记录；已开始到期未归还时保留名额，管理员核实任务完成后释放。

- AC-011-1：已开始的名额到期未归还，标逾期但不分给下一人；核实任务完成后可释放。
- AC-011-2：普通成员按卡确认完成并归还后立即释放，不需管理员审批；归还 GPU 2 不释放同申请的 GPU 3。重复请求不得重复释放，见 NFR-001。

### 4.4 续期、干预与追溯

**FR-012 续期申请与审核。** 成员可申请续期，管理员批准后累计使用时间可超过 3 天。

- AC-012-1：仅提交续期申请不能自动延长当前名额；批准后按批准时长更新期限并通知。
- AC-012-2：续期不设单次或累计时长上限，不得以首次申请 3 天上限直接拒绝累计超过 3 天的已批准续期。逾期但名额尚未释放时，仍可申请和批准续期；新期限在当前时间之后时不再显示为逾期。
- AC-012-3：先批准续期时，后续到期按新期限判断。先释放原名额时，后续对它的续期审批失效，旧名额和后继期限均不改变。分别按两种顺序验收。
- AC-012-4：未开始的6小时名额批准延至原分配后12小时，12小时到期未开始则释放；批准延至原分配后24或30小时，原分配满24小时仍未开始先标异常保留。未批准申请不改变原期限和分支，24小时阈值不重置，已标异常不因延期消除。按 AC-012-3 分别检查两种操作顺序。

**FR-013 管理员干预。** 管理员可审批、调序、代归还、直接延长时长及撤销使用权。

- AC-013-1：每种干预均须填写理由，产生通知并留下操作前后状态；缺少理由不得完成干预。
- AC-013-2：调序可以突破等待提升，但不得隐去发生过人工干预的事实。
- AC-013-3：管理员直接延期成功后到期时间按指定值更新；代归还成功后该名额结束；合法调序成功后目标等待项按指定顺序参与后续分配。每种成功操作均须同时满足理由、通知和审计要求。

**FR-014 即时撤销与线下交接。** 撤销不要求任务已完成；撤销后可重分配，由管理员线下通知原成员停止使用并协调交接。

- AC-014-1：撤销已开始的名额后记录结束，下一申请可获配；系统不发送终止进程指令。
- AC-014-2：界面说明撤销名额不会终止原任务，管理员仍承担交接责任。实际占用冲突不能被记录唯一性测试判为不存在。

**FR-015 站内消息。** 第一版使用网页内站内消息，所有管理员干预必须通知受影响成员。

- AC-015-1：批准、拒绝、调序、代归还、直接延期和撤销后，受影响成员能在站内查看对应操作及原因。
- AC-015-2：获配、异常、逾期、自动释放均向相关成员发送站内消息；每类事件分别验收对应名额和结果。
- AC-015-3：站内消息支持未读/已读状态，标记已读后重新查看仍为已读；邮件/短信不作为验收依赖。

**FR-016 状态审计与记录。** 保留申请、分配、归还记录及管理员干预前后状态，以便解释名额变化。

- AC-016-1：任取一次管理员干预，可关联具体申请/名额并看到操作者、时间、理由及前后状态；完整性见 NFR-003。
- AC-016-2：不能用新状态覆盖此前干预证据，第一版不自动删除记录。管理员可查完整审计，成员通过自己的记录和相关站内消息查看结果；他人公开范围仅限在排姓名与顺序。

**FR-017 查看自己的申请与名额。** 成员能查看自己的按卡等待、部分获配、使用状态和各卡期限。

- AC-017-1：同一申请一张卡获配、一张卡等待时，页面分别显示两卡状态，不能把整份申请显示为全部获配。
- AC-017-2：每个已获配名额展示对应 GPU、分配时间、到期时间及未开始/已开始/异常/逾期状态；两卡不同时间获配时分别展示期限。
- AC-017-3：释放或撤销后，不再将该名额展示为当前有效使用权；本人历史记录仍可辨认。

**FR-018 查看在排队列。** 成员可查看各 GPU 当前在排人员的姓名和顺序。

- AC-018-1：队列中的姓名与顺序对应 FR-007 当前有效排序；部分获配后只在尚未获配卡的队列保留对应等待项。
- AC-018-2：同一成员重复排同一卡时按不同等待项显示其实际位置，不因姓名相同合并；他人申请详情、名额详情和审计不得随队列查询返回。

### Additional Requirements

- AR-01：Vue 3 官方 create-vue、Spring Boot 3.3.13、Java 21、H2 文件库及模块化单体。工程初始化纳入 Story 1.1。
- AR-02：建工程时核实 JDK、Maven、Node，锁定实际 Vue、H2 和新增依赖，记录 H2 文件路径。
- AR-03：名额应用服务唯一写入口；Controller、扫描器及后台CRUD不绕过它，策略层不依赖HTTP（AD-1）。
- AR-04：顺序演示用普通应用事务，服务按当前名额和有效队列处理分配、入队及调序（AD-2）。
- AR-05：current_allocation.gpu_id主键、allocation_id唯一，并通过同卡外键匹配分配历史；映射是唯一有效性权威；异常/逾期仍占名额（AD-2）。
- AR-06：每轮分配使用独立 allocation_id；旧归还、撤销或到期仅针对原名额，不影响后继（AD-3）。
- AR-07：依据业务状态识别重复开始、归还、审核或已读；成员有意重新提交仍产生独立申请（AD-3）。
- AR-08：到期与续期读取当前身份、状态和期限，用可注入 UTC 时钟；保留未开始异常，已结束不复活（AD-4）。
- AR-09：业务、映射、审计及站内消息同事务，必需写入失败整体回滚，事务内无外部 I/O（AD-5）。
- AR-10：业务状态无变化不产生通知，新期限后的再次逾期可产生新通知（AD-5）。
- AR-11：每 60 秒扫描及启动补查数据库，覆盖到期、24 小时未开始和空闲有等待项，按当前状态经名额服务处理（AD-6）。
- AR-12：排序查询与分配共策略和评价时间；原提交时间/receive_seq保持，部分分配不重置，公开只投影姓名和顺序（AD-6）。
- AR-13：按 AD-7 在基础排序后按移动记录 ID 重放，后继紧前优先，前驱紧后备选，均无效则不移动，目标离队后规则失效。
- AR-14：本机同源 HTTP，Session Cookie 为 HttpOnly，保留 CSRF、角色、本人归属和口令散列，通过本地受控步骤建初始管理员（AD-8）。
- AR-15：使用 UTC 时间、字符串 API 标识及 ISO 8601 带 Z，界面为 Asia/Shanghai。H2 保存带时区的时刻。按架构使用 401/403/409/400。
- AR-16：版本化迁移，禁止自动改表；持久化库/迁移工具在基础故事确定；申请整体状态从按卡关系推导，不独立维护可能漂移的整单状态。
- AR-17：单实例同源运行，开发及演示使用独立数据目录，测试使用临时文件库。数据库文件和凭据不入 Git。
- AR-18：本机可复现启动及重启，应用停止后手动备份，在独立副本恢复并核对映射和历史后补查。
- AR-19：按验证计划使用独立 H2 文件库，顺序验证同卡唯一、旧名额、续期与到期、代表性回滚、恢复、排序及权限，保存操作顺序及结果。
- AR-20：至少3个史诗、12个故事、项目上下文至少8实现规则；现有8条ADR继续引用，不等于后续实现规则文件已完成。保存冲刺历史、测试证据、真实人机决策及AI使用声明。
- AR-21：实验A保留，X提供PRD/架构ADR/项目上下文/故事卡，Y干净会话仅口述；同操作者同一天同宿主模型同审查标准。选难度相当故事并测量；实验B排除，不虚构测试、实验或否决记录。
- AR-22：Q09公平性观察由需求负责人在试用评价设计前确定，Q10实验A指标与分工由课程交付负责人在实验设计前核对；不承诺3天内获配，不把名额获配当作硬件利用率。

未发现独立DESIGN.md/EXPERIENCE.md或其他UX设计契约，本次不虚构UX-DR。页面行为沿用PRD的申请、队列、本人名额、消息及管理员操作要求；视觉令牌、组件与布局细节仍待UX/对应故事确定，不新增未经确认的设计指标。

“主归属”用于后续故事责任分配；“扩展/回归”明确跨史诗的验收，不将同一FR重复计为已全部实现。

| FR | 主归属 | 扩展/回归边界 |
| --- | --- | --- |
| FR-001 | Epic1 | Epic2/3逐个新增接口验证角色和归属隔离 |
| FR-002 | Epic1 | Epic2按所选卡分配，不替卡 |
| FR-003 | Epic2 | Epic3紧急申请复用合法时长/入队规则 |
| FR-004 | Epic2 | Epic3排序例外不得按同人重复合并 |
| FR-005 | Epic3 | 审批前/拒绝后沿用Epic2普通等待 |

I want 选择指定GPU和预计使用时长提交普通申请，并查看自己的申请已按卡入队，
So that 我的使用需求被准确记录，无需纸质登记或管理员审批。

**关联要求：** FR-003、004的提交和重复排队；FR-002指定资源身份；FR-006的按卡等待关系；FR-017的本人申请查看基础；FR-001及NFR-002本人归属；AR-03–07、09、12、15–16；AD-1–3、5–6、8。

**依赖与范围：** 依赖 Epic1 的账号、Session 和 GPU 目录。交付选择卡及时长的表单、普通申请和按卡等待项、本人申请查询及必需迁移。普通申请受理后待分配，无需审核。实际获配、公开队列和等待提升由后续故事交付。

**Acceptance Criteria:**

**Given** 成员已登录并能查看10张指定GPU，
**When** 选择一张或多张有效GPU、填写预计使用时长并提交普通申请，
**Then** 创建一份归属于当前Session成员的申请，每张所选GPU各有一个等待项，共享该申请的原提交时间和接收序号，
**And** 直接进入待分配流程而非待审核；返回申请标识和逐卡受理状态，不替换所选卡、不返回虚构名额或到期时间。

**Given** 首次申请时长以整小时填写，
**When** 分别提交1、24、72小时，以及0、负数、非整数、73小时和空值，
**Then** 前三者合法，后五类被服务端拒绝并提示输入问题，
**And** 未选卡或使用不存在的GPU标识也被拒绝，不创建任何部分申请；1天按连续24小时计算，前端校验不能代替服务端校验。

**Given** 成员已提交过包含某张GPU的申请，
**When** 有意再次提交同一卡或另一组卡的申请，
**Then** 正常建立新的申请及独立等待项，不按成员与GPU组合合并、拒绝或给予额外优先级，
**And** 新申请有自己的提交时间与接收序号，不复制旧申请的等待年龄；所有请求的接收顺序持久化，相同提交时间仍可确定先后。

**Given** 已提交的申请属于当前成员，
**When** 成员打开或刷新“我的申请”，
**Then** 能看到本人的申请标识、原提交时间、所选GPU、预计时长和各卡等待状态，
**And** 多卡请求按卡分别列出，不将整份申请标为全部获配；重启后记录仍可查，页面时间按Asia/Shanghai展示，API时间采用带Z的UTC格式且标识为字符串。

**Given** 请求未认证、缺少有效CSRF凭据，或试图伪造申请人/读取他人申请标识，
**When** 直接调用本故事的提交或本人查询API，
**Then** 按权限语义拒绝访问或伪造，不创建归属于他人的申请，不泄露他人申请详情，
**And** 申请归属取自后端认证身份；合法本人提交/查询仍成功，不能靠拒绝全部请求通过验收。

**Given** 普通申请包含多张 GPU，
**When** 通过唯一名额应用服务执行入队事务，
**Then** 同一事务保存申请和各卡等待项，全部必需写入完成后返回成功，
**And** 失败时整体回滚，不留缺卡申请或重复项，不修改已成功申请的原提交时间及接收序号；事务内不做远程训练或其他外部IO。序号允许因回滚出现空洞，不要求连续无缺号。

**Given** 本故事的表单、API和查询均已实现，
**When** 在独立 H2 临时文件库依次验证单卡/多卡、非法输入、有意重复申请、本人查询和越权，
**Then** 保存请求标识、数据库结果和页面结果等证据，可演示提交后按卡入队且由本人查看，
**And** 不依赖后续分配、归还、续期或紧急审批接口；申请受理本身不触发尚未发生的获配通知，也不伪造名额使用状态。

### Story 2.2: 按卡分配普通申请并查看本人名额

As a 实验室成员，
I want 普通申请按各卡当前顺序获得可用名额，并查看哪些卡已获配、何时到期，
So that 我能区分仍需等待的卡和已经取得使用权的卡，按各自期限安排使用。

**关联要求：** FR-002实际指定卡分配、FR-004多卡持有及重复排队、FR-006按卡独立/部分分配、FR-007普通排序/年龄/同时间顺序、FR-008独立计时、FR-015获配消息、FR-016生命周期记录、FR-017本人状态；NFR-001同卡唯一及合法首项获配、NFR-002查询隔离；AD-1–6、8。紧急优先与人工调序随Epic3增加，不在本故事建立未使用的审批或调序表。

**依赖与范围：** 仅依赖Epic1及Story2.1的普通申请和按卡等待项。本故事增加分配历史、唯一当前名额映射、业务转换记录、事务内审计/消息及本人名额展示所需结构；建立唯一分配服务、入队后的分配触发、空闲卡定时补分配和启动补查。本人获配消息至少能在本人消息列表中查阅，已读交互在后续消息故事扩展。开始、归还、到期、续期及公开队列页面不作为本故事前置依赖；测试通过受控数据夹具设置资源初态，不要求这些未来接口存在。

**Acceptance Criteria:**

**Given** 某张GPU没有当前有效名额且存在合法普通等待项，
**When** 入队后触发分配，或后台扫描/启动补查发现该卡可分配，
**Then** 名额服务在事务内读取当前映射和有效排序，使用原 submitted_at 及 receive_seq 选取应获配首项，
**And** 为该卡创建新的 allocation_id 和当前映射，并标记对应等待项已获配。普通申请无需管理员审批。

**Given** GPU2已被占用，GPU3可分配；甲等待GPU2，乙在GPU3有合法首项，
**When** 系统处理两张卡的等待项，
**Then** 甲等待GPU2不能阻止乙获配GPU3，
**And** 每卡保持独立状态和顺序，其他卡的队首不阻塞本卡。

**Given** 一份申请指定GPU2和GPU3，但只有GPU3可分配且该等待项排序符合条件，
**When** 分配成功，
**Then** GPU3显示为获配未开始，GPU2继续等待，整份申请不能显示为全部获配，
**And** GPU2沿用原申请提交时间和接收序号，不因部分获配重置年龄；成员已有其他卡的名额也不阻止合法的新卡分配。

**Given** 同一成员重复申请同一卡，或多名成员在相同提交时间等待该卡，
**When** 选择下一获配者，
**Then** 按各独立等待项的实际顺序分配，相同时间用receive_seq打破并列，不按姓名合并或给同人额外权重，
**And** 普通排序策略使用本次评价时间计算严格超过72小时的等待提升，保留原提交年龄；当前名额已存在时，其余申请继续等待，不创建第二个名额。

**Given** 两张卡分别在t1和t2成功分配给同一份申请，
**When** 成员查看自己的申请和名额，
**Then** 每卡显示GPU标识、allocation_id、分配时间、到期时间和获配未开始状态，到期时间分别从各卡分配记录时间加申请时长计算，
**And** 以应用 UTC 时钟保存各自获配时刻，API 时间带 Z、标识为字符串，界面以 Asia/Shanghai 显示。

**Given** 同一空闲GPU已有明确排序的合法等待项，
**When** 在独立 H2 文件库依次执行分配和重复触发，
**Then** 恰好一个当前名额且属于该时点合法首项，当前映射与同卡历史记录一致；数据库以gpu_id主键、allocation_id唯一及同卡外键阻止重复或悬空映射，
**And** 恰好产生一个有效名额和一次对应获配消息，合法队首须获配。

**Given** 某次分配即将写入当前映射、等待项变化、分配历史、转换序号、审计及获配消息，
**When** 任一必需写入发生错误，包括受检异常或审计/消息保存失败，
**Then** 整个事务回滚，不出现已分配却没有必需记录的结果，不能先通知成功再回滚，
**And** 核对原等待项、当前映射和业务消息均保持事务之前的状态，随后正常处理可完整分配一次。

**Given** 一次分配已成功保存，
**When** 对该卡重复触发分配或扫描，
**Then** 已有有效名额时返回无变化，不产生第二次获配、审计或消息，
**And** 每 60 秒的扫描及启动补查均复用此服务。

**Given** 成员甲、成员乙和未认证请求分别查询名额或获配消息，
**When** 直接请求本人或替换为他人的标识，
**Then** 甲能查询自己的等待/部分获配及获配消息，乙和未认证请求不能读取甲的名额、申请详情、消息或审计，
**And** 加载或持久化失败显示明确错误，不展示虚构获配状态；合法本人请求必须通过，获配记录不被描述为硬件实际空闲或训练已启动。

**Given** 本故事已实现，且数据库已提交等待项但分配触发前应用被停止，
**When** 应用恢复并执行启动补查，或定时扫描发现空闲卡及等待项，
**Then** 能重新发现并分配合法首项，不依赖丢失的内存事件；已有名额保持不变，重复补查无重复副作用，
**And** 保存排序、部分获配、同卡唯一、重复触发及恢复结果。归还、到期和续期在后续故事验收。

### Story 2.4: 成员按卡确认完成并归还名额

As a 持有GPU名额的实验室成员，
I want 完成使用后按卡确认归还，
So that 当前使用权立即结束，后续成员能按顺序获得该卡名额。

**关联要求：** FR-011、AC-011-2；FR-006按卡分配、FR-016历史记录、FR-017结束后的本人状态；FR-015后继获配消息；NFR-001重复归还及旧名额保护、NFR-002本人权限；AD-1–6、8。只更新名额记录，不检查或停止服务器任务；成员对“完成”的声明不能当作硬件监测证据。

**Given** 归还已成功提交但客户端未收到响应，或成员对旧名额再次提交归还，
**When** 重复归还已结束的原名额，
**Then** 返回可辨认的已结束且无变化结果，
**And** 保留首次结束时刻，不重复分配、审计或通知。

**When** 重放A101归还请求，包括同人再次持有该卡或旧前端页面再次提交的情况，

**And** 归还仅按原 allocation_id 操作，不能因 GPU 或成员相同而结束后继名额。

**Given** 请求未登录、缺少有效CSRF凭据或来自其他成员，
**When** 绕过页面直接请求归还并伪造成员、GPU或名额标识，
**Then** 按认证、归属及状态语义拒绝且不暴露他人详情，不改变旧名额、新名额或等待项，
**And** 合法本人归还能成功；管理员代归还不借用此本人接口绕过独立管理员权限与理由要求，后续单独交付。

**Given** 本故事已实现，
**When** 在独立 H2 文件库顺序验证归还、多卡隔离、有无后继、同人再次获配、重复/旧操作及权限，
**Then** 保存操作顺序、映射、历史、消息数量及页面结果，
**And** 到期、续期及撤销的组合情境由对应故事验收。

### Story 2.5: 自动处理到期与未开始异常

As a 持有或等待GPU名额的实验室成员，
I want 系统按既定时间规则处理未开始和逾期名额，并告知相关结果，
So that 短时未开始名额能够重新分配，需要核实的名额不会被误释放。

**关联要求：** FR-010、AC-010-1–4；FR-011 的逾期保留；FR-015–017 通知、记录、本人状态；NFR-001、002；AD-1–6、8。异常和逾期的管理员核实释放由 Story 2.6 交付。

**依赖与范围：** 复用 Story 2.2 的扫描、启动补查、分配及消息和 Story 2.3–2.4 的开始归还。增加短时自动释放、24 小时未开始和已开始逾期状态，始终按原名额当前记录处理。续期场景由 Epic 3 验收。

**Acceptance Criteria:**

**Given** 首次申请不足24小时且名额仍有效、未确认开始，
**When** 到期检查读取该 allocation_id 的当前期限和开始状态，
**Then** 结束原名额并以UNSTARTED_EXPIRED记录原因、移除其当前映射，按已有分配策略为合法下一项创建新名额，
**And** 自动释放消息、原名额结束、后继分配及其获配消息/审计同事务提交；覆盖1、6、23小时，到期前不提前释放，无等待项时不创建虚构名额。

**Given** 申请时长为24小时或超过24小时，且分配后仍未开始，
**When** 距分配满24小时后扫描检查该名额，
**Then** 标记未开始异常、保留当前名额，并向成员生成一次异常消息，
**And** 恰好24小时到期也先标异常等待核实，不直接释放；超过24小时的申请后来达到期限且仍未开始时，继续保留该异常名额，不自动转给下一人；覆盖24、25和72小时。

**Given** 当前有效名额已确认开始且期限已经到达，
**When** 到期扫描读取该名额最新记录，
**Then** 本人页面显示逾期，名额继续有效，等待项不能占用该卡，
**And** 产生对应本次期限的逾期消息和转换记录；不终止训练进程，也不以名额到期推断任务已完成。

**Given** 同一名额的异常、逾期或自动释放已成功处理，
**When** 后续轮次再次扫描或依次处理同一候选，
**Then** 未变化状态不重复产生成功转换、消息或后继分配，首次异常事实不被覆盖，
**And** 通知去重以实际业务转换及当前期限的处理事实判断，不能每扫描一次就生成新的业务事件；后续延期产生的新期限仍须可被再次检查和通知，不能只按allocation_id永久吞掉后续事件。

**Given** 不足 24 小时的未开始名额，分别安排开始在到期检查前及到期释放后，
**When** 分别强制“开始先提交”和“自动释放先提交”两种顺序，
**Then** 前者的到期处理重读到已开始状态，按逾期保留；后者的迟到开始不能复活旧名额或改变后继名额，
**And** 以处理时保存的最新状态和应用 UTC 时钟判断，回滚不会产生有效转换。

**Given** 归还与到期按两种先后顺序处理，或旧名额 A101 已结束且 A102 已获配，
**When** 分别执行两种提交顺序并重放A101旧到期候选，
**Then** 只结束对应有效原名额一次，A102身份、期限及开始事实不被旧候选改写，同人再次获配也不例外，
**And** 归还先发生则旧到期无变化，短时自动释放先发生则旧归还返回已结束。异常或逾期标记本身不释放名额，后续合法归还仍可结束它。

**Given** 应用在名额到期前停止，停机期间跨过短时到期或24小时未开始阈值，
**When** 应用重启并从数据库补查，再重复进行正常扫描，
**Then** 发现候选并按当前持久化状态处理，已有后继不受影响，
**And** 保留原分配时间、期限和 60 秒扫描间隔，停机期间不即时处理。

**Given** 成员查询本人名额、异常或逾期消息，其他成员尝试替换标识，
**When** 调用本人查询API或尝试从浏览器调用内部扫描处理入口，
**Then** 本人可见正确按卡状态和消息，他人详情仍被拒绝，普通成员不能触发任意名额的系统身份处理，
**And** UI不能以硬件实测空闲或训练完成描述这些记录；管理员核实释放及续期功能不在本故事暗中增加。

**Given** 本故事及全部前序故事已实现，
**When** 在独立 H2 文件库使用可控时钟，按顺序检查时间边界、旧名额和重启补查，
**Then** 保存操作顺序、名额 ID、时间、当前映射、历史与消息证据，
**And** 续期和管理员核实由对应故事验收。

### Story 2.6: 管理员核实异常或逾期后释放名额

As a 算力管理员，
I want 查看未开始异常或逾期名额，在线下核实后带理由确认释放，
So that 需要人工处理的名额能够安全结束并交给后续成员，处理依据也可追溯。

**关联要求：** FR-010异常核实、FR-011逾期核实任务完成后释放；FR-013的理由/通知/审计基础；FR-015–017消息与历史；NFR-001旧事件及重复处理、NFR-002管理员权限、NFR-003本操作审计完整性；AD-1–6、8。无需等待任务完成的主动撤销仍属Epic3/FR-014，本故事不能用“核实释放”绕过完成条件。

**依赖与范围：** 依赖 Story 2.4 的释放/分配事务及 Story 2.5 的异常和逾期状态。交付管理员待处理列表、核实详情、确认理由、释放及其审计通知。名额仍有效但所见状态有变化则刷新重新核实。

**Acceptance Criteria:**

**Given** 当前存在未开始异常或已开始逾期且仍有效的名额，
**When** 管理员登录后查看待处理列表和详情，
**Then** 显示 GPU、原名额 ID、成员、分配、开始和到期事实，以及当前异常或逾期条件，
**And** 信息表达为使用权记录，不显示虚构的实时进程状态；已结束名额不再作为可释放项，普通成员不能查看该管理列表。

**Given** 管理员尚未核实可释放，或已开始的任务尚未确认完成，
**When** 查看或尝试提交处理结果，
**Then** 不结束名额，不分配给下一人，
**And** 页面说明先线下核实；提交释放必须填写非空理由并确认核实条件：未开始异常需核实可释放，已开始逾期需核实任务完成。理由或确认缺失的直接API请求也拒绝，不能仅靠前端控件检查。

**Given** 管理员核实目标可释放，并提交 allocation_id、所见状态、确认及非空理由，
**When** 名额服务核验管理员角色，读取最新映射和状态，
**Then** 仍匹配有效异常或逾期名额且状态一致时，结束原名额并保存 VERIFIED_RELEASED，
**And** 同事务中移除旧映射、给存在的合法首项创建新名额、记录完整审计，并通知原成员处理原因及后继成员获配；没有等待项时不虚构后继。成功响应等待事务提交完成。

**Given** 管理员查看后成员已确认开始、归还或名额发生其他状态变化，
**When** 管理员依据已变化的所见状态提交核实释放，
**Then** 原名额仍有效时返回 409 并要求刷新核实；若已结束，返回已处理或失效，
**And** 不复用旧确认改变最新名额；若仍是同一有效名额但由未开始变为已开始，须重新依据当前任务是否完成核实，不能将原“未开始可释放”的判断自动沿用。

**Given** 原名额已核实释放，
**When** 重复请求释放已结束的原名额，
**Then** 返回失效或已处理，名额状态无变化，
**And** 最多结束原名额一次并产生一个合法后继名额，不重复成功审计或业务通知；即便下一次持有者相同，旧allocation_id也不能作用于新映射。

**Given** 本操作释放成功，
**When** 管理员查询处理记录，原成员查询本人名额、历史和消息，
**Then** 管理员能查到操作者、操作时间、名额、理由和前后状态，原成员收到已结束通知，
**And** 历史不被覆盖或自动删除，成员不因该通知获得查看其他成员详情或完整管理员审计的权限；消息只说明已记录的处理结果，不宣称系统已停止任务。

**Given** 请求未登录、缺少有效CSRF凭据或来自普通成员，
**When** 直接调用核实详情、处理记录或核实释放入口并伪造角色/成员/名额标识，
**Then** 按权限语义拒绝管理查询或状态变更，不泄露其他成员详情且所有名额/队列状态保持不变，
**And** 合法管理员仍能核实释放，合法成员仍能通过本人入口查询自己的结果；不能把本操作实现为所有请求均拒绝。

**Given** 本故事和全部前序故事已实现，
**When** 使用独立 H2 文件库顺序检查核实释放、未确认/缺理由、状态变化、重复/旧请求及权限，
**Then** 保存提交顺序、名额映射、完整审计字段、消息数量及页面结果证据，普通申请闭环可包含人工核实释放，
**And** 不依赖Epic3续期、直接延期、代归还或主动撤销接口；已验证本操作不等于全部管理员操作矩阵已经通过，也不声称线下核实是系统测得的任务状态。

### Story 2.7: 成员查看各 GPU 的公开等待队列

As a 实验室成员，
I want 登录后按指定GPU查看当前在排人员的姓名和顺序，
So that 我能了解资源等待情况，同时不获取其他成员的申请或使用详情。

**关联要求：** FR-018、AC-018-1–2；FR-007普通排序及等待年龄；FR-004重复排队；FR-006部分分配；FR-001及NFR-002公开字段边界；AD-1–2、6、8。紧急申请和人工调序在Epic3补充回归，不在本故事提前实现相关写入口。

**依赖与范围：** 依赖已交付的GPU目录、普通等待项和分配策略，复用现有Session。包含逐卡队列页面、受保护只读API、空态/加载/错误反馈和字段裁剪验证；不新增独立“页面排序”算法或复制一份队列权威数据。本人申请详情继续由既有本人入口提供，公共列表不会因浏览者是本人而顺带返回其他人详情。

**Acceptance Criteria:**

**Given** 成员已登录，指定GPU有一个或多个有效等待项，
**When** 打开该卡的公开队列，
**Then** 按等待项逐条显示在排人员姓名和当前顺序，并明确所对应的GPU，
**And** 仅包含尚未获配的等待项，已获配、已结束名额不作为在排项；无等待项显示真实空队列，不把它解释为GPU硬件实际空闲。

**When** 对相同有效队列快照和同一评价时间进行查询与分配候选选择，
**Then** 两者使用同一排序策略，顺序一致，时间并列按持久化接收先后稳定排序，严格超过72小时的判断与既定规则相同，
**And** 查询不重写提交时间或接收序号，不另算一个与分配服务不一致的名次；紧急/调序尚未上线时也不捏造其效果。

**Given** 同一申请包含GPU2和GPU3，GPU3已部分获配而GPU2仍等待，
**When** 分别查询两张卡的公开队列，
**Then** 该申请只在GPU2对应队列保留等待项，GPU3不再显示该项在排，
**And** GPU2等待年龄沿用原提交时间；查询不以整单状态把两张卡一起移出或一起保留。

**Given** 同一成员有意多次申请同一卡，或多个成员使用相同显示姓名，
**When** 查询公开队列，
**Then** 按真实等待项分别显示姓名与各自位置，不按姓名或成员合并去重，
**And** 成员不因同名或重复申请获得额外优先级，显示顺序仍与分配策略一致；不为区分同名而额外公开账号标识或申请详情。

**Given** 成员请求队列API，包括直接调用或增加详情/成员标识等伪造参数，
**When** 服务端生成公共队列响应，
**Then** 在指定GPU上下文中只公开等待人员姓名和顺序，不返回其账号ID、申请ID、名额ID、时长、申请详情、使用详情、消息或完整审计，
**And** 未认证访问被拒绝，公共查询不能借参数切换为他人详情查询；检验原始响应而非仅检查前端未显示，合法登录成员仍能读取队列。

**Given** 上一次查询后已入队或完成分配，或发生网络/数据库查询失败，
**When** 页面加载或刷新某张卡的队列，
**Then** 单卡结果来自一致的有效队列快照和评价时刻，后续刷新可反映已提交变化；加载和失败状态可以辨认，失败不伪装为空队列，
**And** 查询本身不触发分配、延长等待年龄或修改名额；不承诺页面显示后队列永远不变，不用缓存旧结果证明下一次分配越序。

**Given** 本故事已实现，
**When** 在独立测试库检查空队列、普通顺序、并列时间、72 小时边界、同名/重复申请、部分分配及越权字段，
**Then** 保存相同快照下的公共顺序与分配候选、原始JSON字段、页面状态及权限结果等证据，
**And** 不依赖未来紧急审批或调序接口即可通过；这两类优先级加入后须回归同一查询入口，而非创建另一个公开排序来源。

### Story 2.8: 成员查看站内消息并标记已读

As a 实验室成员，
I want 查看与本人相关的站内消息，并将已处理的单条消息标记为已读，

**关联要求：** FR-015、AC-015-2–3；FR-015核实释放相关管理员通知基础；FR-001本人可见范围及NFR-002；AD-1、5、8中通知模块与事务边界。Epic3各类新管理员干预须继续向同一个收件箱写入并回归，不在本故事预先增加这些操作。

**依赖与范围：** 复用前序故事已与业务同事务产生的消息记录及本人查询基础，扩展完整收件箱页面、本人消息查询和单条已读命令，以及必要的read_at字段和验证。消息生成责任仍在对应业务事务；本故事不重新扫描或补造业务消息，不引入邮件、短信或独立消息队列。候选交互是成员明确点击“标记已读”后才持久化已读状态；不增加批量操作、标回未读或删除能力。

**Acceptance Criteria:**

**Given** 同一消息已标记已读，

**Then** 返回可辨认的已读成功/无变化结果，保留首次read_at，不出现重复消息或相互覆盖状态，
**And** 其他消息不变，期间新增的业务消息仍为未读。

**Given** 一条消息关联的名额后来已经归还、结束或被后继名额替换，
**When** 成员查阅或标记这条历史消息，
**Then** 消息仍可阅读并保留其原本业务含义，已读操作不修改名额、队列、原审计或消息正文，
**And** 不重新触发分配、释放、异常处理或发送业务消息；历史消息不能作为恢复旧名额或访问新持有者详情的入口。

**Given** 请求未登录、标记命令缺少有效CSRF凭据，或成员替换消息ID/收件人参数试图查看或修改他人消息，
**When** 直接请求消息列表、单条内容或已读API，

**And** 归属依据Session身份而非客户端成员字段；管理员身份也不通过本人收件箱接口任意查看他人消息，合法本人查询及标记必须成功。

**Given** 加载消息失败或已读写入失败，
**When** 页面查询或提交单条标记，
**Then** 展示可辨认的加载/错误反馈，不把失败当作空收件箱或已持久化成功，
**And** 重查以实际持久化状态为准，重复操作保留首次已读时间。

**Given** 本故事及其前序已实现，
**When** 在独立测试库检查各类消息、明确标记、重启后已读、重复标记、历史、归属和写入失败，
**Then** 保存收件人、消息记录、read_at及页面/API结果等证据，已提交业务消息可由本人阅读且状态持久，
**And** 此故事无需未来紧急审批、调序、续期或撤销接口即可通过；业务与通知同事务的原有故障验收仍由生成消息的前序故事承担，不因本故事存在而推迟或省略。
