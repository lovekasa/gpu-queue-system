# gpu-queue-system - Epic Breakdown

## Overview

3个史诗下的20条故事均已获批，最终规格验证已通过，工作流已完成。需求沿用PRD原编号。

## Requirements Inventory

### Functional Requirements

验收条目标识采用 AC-三位 FR 编号-序号，例如 AC-001-1。下列“验收”是将来应执行的检查，不是已完成结果。

### 4.1 身份与资源

**FR-001 身份与角色隔离。** 系统区分成员与算力管理员，账号由管理员创建。

- AC-001-1：成员尝试紧急审批、续期审批、调序、代归还、直接延期或撤销时，操作被拒绝且业务状态不变。
- AC-001-2：成员可发起自己的续期申请，不能把申请操作变成直接延期。
- AC-001-3：管理员可创建成员账号；成员不能自行注册或创建账号、授予管理员权限。
- AC-001-4：成员可查看本人申请、名额和通知；他人在排队列仅公开姓名及顺序，不暴露其申请详情、使用名额详情、通知或完整审计。管理员可查看处理申请及审计所需记录。

**FR-002 指定 GPU 识别。** 提供 10 张 GPU 的独立标识，申请和分配均指向具体卡。

- AC-002-1：申请 GPU 2 获配后，记录显示 GPU 2，不替换成其他卡；资源页面明确描述为名额状态，不宣称实测 GPU 空闲。

### 4.2 申请与排队

**FR-003 普通申请。** 成员可选择一张或多张指定 GPU 并填写首次预计使用时长，普通申请免审批，首次时长最多 3 天。

- AC-003-1：合法普通申请提交后无需管理员审批即可进入等待/分配流程。
- AC-003-2：首次时长仅接受 1–72 的整数小时；1、24、72 小时合法，0、负数、非整数及 73 小时被拒绝。

**FR-004 重复排队与多卡持有。** 允许成员多次排队并同时持有多张不同 GPU。

- AC-004-1：持有 GPU 1 的成员仍可申请 GPU 2；不能仅因已有名额拒绝申请。
- AC-004-2：同一成员重复申请同一卡时，各申请按与其他成员相同的优先级规则正常排队；不得因同一申请人而额外提升或降低优先级，也不得合并或拒绝重复申请。同一卡仍最多一个有效名额。

**FR-005 紧急申请审核。** 紧急申请必须由管理员批准后才获得紧急待遇。

- AC-005-1：未经批准的申请不能按“已批准紧急”优先级参与分配；批准/拒绝须保留理由、通知和审计。
- AC-005-2：紧急审批前按普通申请等待，可按普通规则获配；批准不能重复分配已获配的卡。驳回后继续普通排队，原提交时间不变。

**FR-006 按卡排队与部分分配。** 每张卡独立竞争，多卡申请可以分批获得名额，不让不冲突的 GPU 被全局队首阻塞。

- AC-006-1：甲等待忙碌 GPU 2，乙申请空闲 GPU 3；甲的等待不能阻止乙获得 GPU 3。
- AC-006-2：甲申请 GPU 2、3，只有 GPU 3 可分配且甲在该卡符合顺序时，可先分 GPU 3，GPU 2 保持等待。
- AC-006-3：同一卡按 FR-007 的当前有效排序分配，不得绕过排序在前的等待项；同人重复申请同一卡也适用。

**FR-007 时间顺序与等待提升。** 普通申请按提交时间排序；等待超过 3 天可超过紧急申请；管理员手动调序可突破此保障。

- AC-007-1：无管理员干预和其他优先条件时，普通申请中先提交者先获得该卡。
- AC-007-2：等待从申请提交时起算，恰好 3 天不触发“超过”，超过 3 天可排在紧急申请前；部分获配后其余卡仍沿用原提交时间，不重置等待年龄。
- AC-007-3：无人工调序时，等待超过 72 小时的等待项排在已批准紧急项之前，后者排在其余普通项之前；每组按原提交时间排序。相同提交时间使用系统接收先后固定排序，刷新页面不得改变顺序。
- AC-007-4：管理员调序仅对当前指定等待项有效，不形成成员永久优先级，也不继承到该成员的新申请或其他等待项。当前项获配结束等待后，该项调序不再作用于后续申请。此规则不保证 3 天内获配。

### 4.3 分配、开始与结束

**FR-008 按卡独立计时。** 每张 GPU 从其各自分配成功起计算使用期限。

- AC-008-1：同一多卡申请在 t1、t2 分别获配两张卡，期限分别从 t1、t2 起算，不能统一从申请提交或第一张卡获配时起算。

**FR-009 确认开始与使用约定。** 成员应先在网页确认开始，再自行运行任务。

- AC-009-1：确认开始只更新名额记录；不触发远端任务执行，也不证明成员遵守约定。
- AC-009-2：成员按卡确认开始，开始 GPU 2 不改变同一申请中 GPU 3 的开始状态。违规运行由管理员线下协调，第一版不增加处罚模块。

**FR-010 未开始异常与短时例外。** 分配后24小时未确认开始先标异常，管理员核实后释放；当前已批准期限总跨度不足24小时的名额到期未开始直接释放，跨度定义见§3。

- AC-010-1：当前已批准期限总跨度超过24小时的名额在原分配后满24小时仍未开始，保留名额、标异常，不能直接分给下一人。
- AC-010-2：当前已批准期限总跨度不足24小时的名额到期仍未开始，释放该名额，允许后续分配；至少覆盖6小时及另一种合法短时名额。
- AC-010-3：恰好 24 小时到期且未开始时，先标异常并等待核实，不能直接释放。
- AC-010-4：不足 24 小时的名额，若到期处理时开始已成功记录，则按已开始到期规则保留名额；若到期释放已成功记录，迟到的开始不得恢复旧名额。两种记录顺序均须验收，不能仅按请求发出时间判断。

**FR-011 归还与逾期处理。** 支持结束使用与归还记录；已开始到期未归还时保留名额，管理员核实任务完成后释放。

- AC-011-1：已开始的名额到期未归还，标逾期但不分给下一人；核实任务完成后可释放。
- AC-011-2：普通成员按卡确认完成并归还后立即释放，不需管理员审批；归还 GPU 2 不释放同申请的 GPU 3。重复请求不得重复释放，见 NFR-001。

### 4.4 续期、干预与追溯

**FR-012 续期申请与审核。** 成员可申请续期，管理员批准后累计使用时间可超过 3 天。

- AC-012-1：仅提交续期申请不能自动延长当前名额；批准后按批准时长更新期限并通知。
- AC-012-2：续期不设单次或累计时长上限，不得以首次申请 3 天上限直接拒绝累计超过 3 天的已批准续期。逾期但名额尚未释放时，仍可申请和批准续期；新期限在当前时间之后时不再显示为逾期。
- AC-012-3：审批时名额已释放，续期不得生效，不得恢复旧名额或改动新持有者的期限；审批先成功记录且延长了期限时，旧到期事件必须按新期限判断，不得按旧期限释放。
- AC-012-4：未开始的6小时名额批准延至原分配后12小时，12小时到期未开始则释放；批准延至原分配后24或30小时，原分配满24小时仍未开始先标异常保留。未批准申请不改变原期限和分支，24小时阈值不重置，已标异常不因延期消除。批准与到期竞争仍按成功记录顺序处理，已结束名额不得复活。

**FR-013 管理员干预。** 管理员可审批、调序、代归还、直接延长时长及撤销使用权。

- AC-013-1：每种干预均须填写理由，产生通知并留下操作前后状态；缺少理由不得完成干预。
- AC-013-2：调序可以突破等待提升，但不得隐去发生过人工干预的事实。
- AC-013-3：管理员直接延期成功后到期时间按指定值更新；代归还成功后该名额结束；合法调序成功后目标等待项按指定顺序参与后续分配。每种成功操作均须同时满足理由、通知和审计要求。

**FR-014 即时撤销与线下交接。** 撤销不要求任务已完成；撤销后可重分配，由管理员线下通知原成员停止使用并协调交接。

- AC-014-1：撤销已开始的名额后记录结束，下一申请可获配；系统不发送终止进程指令。
- AC-014-2：界面说明撤销名额不会终止原任务，管理员仍承担交接责任。实际占用冲突不能被记录唯一性测试判为不存在。

**FR-015 站内消息。** 第一版使用网页内站内消息，所有管理员干预必须通知受影响成员。

- AC-015-1：批准、拒绝、调序、代归还、直接延期和撤销后，受影响成员能在站内查看对应操作及原因。
- AC-015-2：获配、异常、逾期、自动释放均向相关成员发送站内消息；每类事件分别验收对应名额和结果。
- AC-015-3：站内消息支持未读/已读状态，标记已读后重新查看仍为已读；邮件/短信不作为验收依赖。

**FR-016 状态审计与记录。** 保留申请、分配、归还记录及管理员干预前后状态，以便解释名额变化。

- AC-016-1：任取一次管理员干预，可关联具体申请/名额并看到操作者、时间、理由及前后状态；完整性见 NFR-003。
- AC-016-2：不能用新状态覆盖此前干预证据，第一版不自动删除记录。管理员可查完整审计，成员通过自己的记录和相关站内消息查看结果；他人公开范围仅限在排姓名与顺序。

**FR-017 查看自己的申请与名额。** 成员能查看自己的按卡等待、部分获配、使用状态和各卡期限。

- AC-017-1：同一申请一张卡获配、一张卡等待时，页面分别显示两卡状态，不能把整份申请显示为全部获配。
- AC-017-2：每个已获配名额展示对应 GPU、分配时间、到期时间及未开始/已开始/异常/逾期状态；两卡不同时间获配时分别展示期限。
- AC-017-3：释放或撤销后，不再将该名额展示为当前有效使用权；本人历史记录仍可辨认。

**FR-018 查看在排队列。** 成员可查看各 GPU 当前在排人员的姓名和顺序。

- AC-018-1：队列中的姓名与顺序对应 FR-007 当前有效排序；部分获配后只在尚未获配卡的队列保留对应等待项。
- AC-018-2：同一成员重复排同一卡时按不同等待项显示其实际位置，不因姓名相同合并；他人申请详情、名额详情和审计不得随队列查询返回。

### Additional Requirements

- AR-01：Vue3官方create-vue、Spring Boot3.3.13、Java21、本地MySQL模块化单体。Epic1 Story1须包含工程初始化及运行版本核查/锁定；本次只规划，不执行初始化。
- AR-02：工程创建前核实MySQL服务端版本、运行JDK、Maven、Node及前端依赖，缓存Boot POM不代表现有业务工程；数据库客户端实测8.0.34不代表服务端版本。
- AR-03：名额应用服务唯一写入口；Controller、扫描器及后台CRUD不绕过它，策略层不依赖HTTP（AD-1）。
- AR-04：READ COMMITTED事务，先锁固定GPU行；申请入队、紧急审核、调序等同卡排序变更同锁，多卡按gpu_id升序取锁（AD-2）。
- AR-05：current_allocation.gpu_id主键、allocation_id唯一，并通过同卡外键匹配分配历史；映射是唯一有效性权威；异常/逾期仍占名额（AD-2）。
- AR-06：每次分配独立不复用allocation_id，旧归还/撤销/到期不影响后继名额；校验权限后先返回已提交幂等结果，再判断旧名额冲突（AD-3）。
- AR-07：command_id按操作者唯一，保存载荷指纹及结果；同键同载荷返原结果、异载荷409；唯一键竞争失败回滚后读胜出结果，有意重复申请用新键（AD-3）。
- AR-08：续期和到期同锁重读，成功提交顺序决定；锁内数据库UTC微秒时间及transition_seq，回滚无成功；延期不清未开始异常，终态不复活（AD-4）。
- AR-09：业务、当前映射、幂等结果、审计和站内消息同事务；包括受检异常在内必需写入失败全回滚；代理事务真正生效；事务内无外部IO（AD-5）。
- AR-10：有限死锁/超时重试，原command_id保留，次数与超时在运行故事确定；消息按转换ID＋接收者＋类型去重，不吞新期限后的再次逾期消息（AD-5）。
- AR-11：数据库定时扫描和启动补查，候选只提示、锁后重读；覆盖到期、24小时未开始及空闲有等待项，异常不重复通知（AD-6）。
- AR-12：排序查询与分配共策略和评价时间；原提交时间/receive_seq保持，部分分配不重置，公开只投影姓名和顺序（AD-6）。
- AR-13：调序按AD-7固定重放算法：基础列表后按transition_seq重放；原后继紧前优先、原前驱紧后备选、均无效不移动，后操作优先，离队清理；不得生成永久成员权重。
- AR-14：Session、CSRF、口令散列、HttpOnly、本人归属及角色校验；受控初始管理员；开发本机与正式HTTPS配置区分，禁止日志含口令或Session（AD-8）。
- AR-15：API标识为字符串、ISO8601 UTC带Z，库DATETIME(6)及UTC会话，页面上海时区；统一401/403/409/400语义，禁止客户端时间裁决。
- AR-16：版本化迁移，禁止自动改表；持久化库/迁移工具在基础故事确定；申请整体状态从按卡关系推导，不独立维护可能漂移的整单状态。
- AR-17：本地单实例、同源静态资源/API，dev/test/demo库和账号分离，迁移单次执行、应用库限定权限，无Redis/独立消息队列/微服务。
- AR-18：运行可观察进程存活、扫描最后成功/失败、锁超时和回滚计数；试用前备份恢复演练，恢复后核对映射/历史再补扫。
- AR-19：依verification-plan在真实MySQL多独立连接验证30次竞争、不同卡并行、旧事件重放、续期/到期两顺序、故障/响应丢失重试、重启恢复、排序和权限。保存请求/提交序号与最终状态证据；无证据不得判通过。

**When** 任一必需写入失败，包括审计或消息持久化失败，
**Then** 整体回滚，旧期限保持，不出现已延长但缺必需记录的成功状态，
**And** 成功时记录操作者、数据库时间、理由、目标名额及前后期限/状态，向持有者既有收件箱写入结果和原因；不覆盖历史、不自动删除，不发送未提交的成功消息。

**Given** 本故事及其前序已实现，
**When** 在独立MySQL测试库验证直接延期、无效输入、跨72小时、逾期及异常名额、短时跨24小时、各竞争顺序、幂等、权限及失败回滚，
**Then** 保存新旧期限、名额ID、数据库时间、transition_seq、当前映射、完整审计及消息数量的证据，
**And** 不依赖未来管理员代归还或主动撤销接口；不得用页面时间变化代替锁内数据及独立连接并发检查。

### Story 3.5: 管理员带理由代成员归还名额

As a 算力管理员，
I want 在核实成员已结束使用后，带理由代为归还指定名额，
So that 成员未自行操作时资源仍能完成交接，且真实操作人和依据可以追溯。

**关联要求：** FR-013、AC-013-1及AC-013-3的代归还；FR-011完成后释放及FR-015–017通知、记录和本人状态；NFR-001重复释放/旧名额、NFR-002管理员权限、NFR-003本操作完整审计；AD-1–6、8。系统不核查或停止训练进程。无需等待任务完成的主动撤销仍在下一条故事，不能通过代归还绕过核实条件。

**依赖与范围：** 复用Story2.4的归还/后继分配、Story2.6的管理员核实与版本校验，以及既有收件箱和完整审计。扩展为对当前有效名额代归还，不限于异常/逾期列表。已确认交互为管理员查看成员、GPU、allocation_id及最新名额版本，确认已核实使用结束后，填写非空理由并提交command_id；已开始名额需确认任务完成，未开始名额需核实可以结束使用权。只归还指定名额，不代替成员身份登录或伪造成成员本人操作。

**Acceptance Criteria:**

**Given** 管理员已登录，某个成员有一个仍有效的GPU名额，
**When** 查看该名额详情并发起代归还，
**Then** 能识别成员、GPU、原名额ID、开始/到期事实及所见状态版本，并看到需核实使用结束的确认项，
**And** 不要求名额已经异常或逾期才允许进入流程；页面不将数据库记录当作真实任务状态，不能通过代归还执行无需核实的主动撤销。

**Given** 尚未确认任务完成/未开始可释放，或管理员没有提供非空理由，
**When** 从页面或直接API提交代归还，
**Then** 服务端拒绝处理，原名额和队列不变，
**And** 已开始任务仍在进行时不能确认代归还成功；系统记录的是管理员线下核实声明，不以技术探测或自动停止任务来补足条件。

**Given** 管理员已完成核实并提交目标allocation_id、所见版本、理由及command_id，
**When** 名额服务验证管理员角色并锁定该GPU，锁后身份/有效状态及版本校验通过，
**Then** 结束该原名额、保存RETURNED结束原因，并通过操作类型及实际操作者明确是管理员代归还，不能伪造成成员本人操作，
**And** 释放、合法下一等待项的新名额分配、幂等结果、完整审计、原成员处理通知及后继获配消息同事务提交；无等待项时不创建虚构名额或消息。

**Given** 成员还持有其他卡、同申请仍有卡等待，或者原成员也是下一项合法获配人，
**When** 管理员只代归还指定名额，
**Then** 只结束目标名额，其他卡及等待项不被整单归还，原成员可查已结束历史及处理原因，
**And** 后继即使属于同一成员也使用新的allocation_id和独立期限，旧命令不能再释放它；历史与审计不被覆盖或自动删除。

**Given** 管理员查看后发生本人归还、到期处理、续期或直接延期，或两个管理员同时操作，
**When** 提交代归还或重放旧请求，
**Then** 同键成功结果经权限验证后优先返回；原名额仍有效但所见状态版本变化时409并刷新核实，已结束时新请求返回失效/已处理且无变化，
**And** 不恢复旧名额或触碰后继；并发操作按同卡成功提交顺序处理，最多结束原名额一次。同键异载荷409，不重复成功审计、处理通知或后继获配。

**Given** 请求未认证、缺少有效CSRF凭据，或普通成员伪造管理员角色直接调用代归还，
**When** 请求管理详情或代归还API，
**Then** 后端拒绝越权读取和变更，所有名额、队列及他人信息不受影响，
**And** 合法管理员操作可成功，普通成员仍通过已有本人归还入口结束自己的使用，不将代归还能力扩散给成员；原成员只在本人入口看到获准范围的结果。

**Given** 代归还及后继分配、幂等结果、审计和全部必需通知在同一事务保存，
**When** 任一必需步骤失败，包括审计或消息写入错误，
**Then** 整体回滚，原名额保持有效，不向页面报告成功，不留下无法追溯的释放或未提交的通知，
**And** 复用原command_id按既定有限重试约定可完成一次完整操作，数据库时间和transition_seq可追溯，不在事务内进行远程训练操作或等待人工核实。

**Given** 本故事及其前序已实现，
**When** 在独立MySQL测试库验证正常/异常/逾期名额的代归还、缺核实/理由拒绝、多卡隔离、同人再获配、旧请求、双管理员及本人归还/到期/延期竞争、权限和回滚，
**Then** 保存提交顺序、名额ID及映射、前后状态、真实操作者、理由、审计和消息数量的证据，
**And** 无需未来主动撤销接口即可通过；已验证此操作不能冒称所有管理员操作或线下核实真实性均已由系统自动验证。

### Story 3.6: 管理员主动撤销名额并协调线下交接

作为管理员，我希望必要时能立即结束指定成员的 GPU 使用权，并通知原成员停止使用，以便下一位成员获配后能与原成员协调实际交接。

**关联要求：** FR-013–017、AC-014-1、AC-014-2、NFR-001–003。复用同卡事务、名额身份校验、收件箱与审计。

**Acceptance Criteria:**

**Given** 管理员查看仍有效的名额，即使任务仍在运行，  
**When** 打开撤销确认页，  
**Then** 页面展示成员、GPU、目标名额，并明确提示撤销成功后可立即重新分配，原进程可能继续运行，  
**And** 提醒管理员线下通知原成员停止使用、协调双方交接。提交无需任务完成证明或成员回执。

**Given** 管理员提交目标 allocation_id、所见版本、非空理由和 command_id，  
**When** 服务端锁定该 GPU 并验证当前名额和版本，  
**Then** 将该名额记为已撤销，记录实际管理员、时间、理由和前后状态，并向原成员发送撤销通知，  
**And** 其他卡的名额与等待项保持原状。系统不发出停止训练的指令。

**Given** 同卡有合法等待项，  
**When** 撤销事务提交，  
**Then** 队首获配全新的名额 ID 和独立期限，并收到获配通知，即使后继与原持有人是同一成员，  
**And** 没有等待项时该卡空闲。成员可查本人结果，系统不会据此宣称物理 GPU 已空闲或交接已完成。

**Given** 归还、到期、延期或另一管理员撤销与本次撤销竞争，  
**When** 锁后复查原名额，  
**Then** 原名额仍有效但版本变化时返回 409，管理员须刷新后重新确认。原名额已结束时，新命令不再变更状态，  
**And** 迟到的归还、到期或撤销事件只针对原名额，后继的名额和期限不受影响。

**Given** 同一管理员已成功撤销，  
**When** 经授权后使用原 command_id 重试，  
**Then** 同载荷返回首次结果，异载荷返回 409，  
**And** 不重复结束名额、分配、写成功审计或发送消息。

**Given** 请求缺少登录、有效 CSRF 凭据、管理员权限或非空理由，  
**When** 通过页面或直接 API 提交，  
**Then** 服务端拒绝变更，  
**And** 原名额和队列保持原状，无成功审计和结果通知。

**Given** 撤销、后继获配、命令结果、完整审计与所需通知属于同一事务，  
**When** 任一必需写入失败，  
**Then** 全部回滚，原名额仍有效，后继未获配，  
**And** 使用原命令重试可完成一次完整交接，不在事务中等待线下协调。

**Given** 实施后使用独立 MySQL 测试库及两个成员账号，  
**When** 验证运行中撤销、有无后继、旧事件、并发重试、权限拒绝及写入失败，  
**Then** 保存映射、历史、通知、审计和事务结果作为证据，  
**And** 单独检查页面的交接提示，将数据库名额唯一性与实际任务是否停止分别记录。
