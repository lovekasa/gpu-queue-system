# 本地课程演示版变更提案

D048 于 2026-11-19 确认本提案。当前约定以修订后的 PRD、架构、故事清单与 SPEC 为准。本文件保留提案时的讨论和实施范围。

## 1. 问题与依据

用户说明三人没有部署服务器，只需本地运行，课程主要考核 BMAD 使用过程，并明确表示“并发这些东西可以不考虑”。此前 MySQL 安装、分库账号、30连接并发、锁与死锁重试使工程准备偏重。目前尚无业务代码、数据迁移或完成的故事，适合先简化规格再开始 Story 1.1。

用户已明确撤回并发方面的实施要求；本提案将 H2 文件模式及相关验收调整一次汇总供确认。H2 是 AI 推荐的具体数据库选型，不将此前询问轻量数据库记为已批准全部技术细节。旧 MySQL 实测信息保留为历史，不再作为拟议版本的运行前置。

无独立 UX 契约；现有页面流程无需因此重做。无业务代码回滚、部署或数据转换；用户已有 MySQL 库不作删除或修改。

## 3. 推荐方案

直接调整现有计划，采用 Vue3、Spring Boot3.3.13、Java21、H2文件数据库的本地单实例演示工程。

- 数据库随后端运行，精确 H2 依赖版本在 Story 1.1 锁定。默认本地文件持久化，测试使用独立临时目录，演示数据与测试数据不混用。
- 启动脚本明确执行版本化迁移后启动应用；无需组员手动创建数据库或账号，不用 ORM 自动改表。
- 演示按一次一个业务操作进行；后台扫描若保留，每60秒检查一次并与页面写入使用同一个简单处理入口，避免扫描与演示操作重叠；不做并发吞吐或多实例承诺。
- 保留基本数据库事务、主键/唯一约束、allocation_id 和状态检查。取消专门的固定GPU行锁、跨卡锁序、死锁自动重试和数据库微秒提交顺序协议。
- 取消通用 command_id 指纹/结果表及同键竞争处理要求；开始、归还、已读和审核等重复操作由当前业务状态识别并返回已处理。重新提交申请仍可产生新的有意申请，不承诺丢失响应后的通用请求幂等。
- 页面仍有基本登录、角色、本人数据归属、口令散列与CSRF；演示只需本机HTTP，不搭正式HTTPS或运维监控平台。
- 业务与必需记录用普通事务一起保存，写入失败显示错误；验证代表性回滚场景，取消逐类故障注入压力矩阵。
- 各成员本机数据独立；GitHub保存代码、迁移、演示种子和交接文档，不提交数据库文件、账号密码或本机运行状态。

工作量：文档调整较小、实现复杂度明显降低；风险主要是旧规则仍被后续agent读取，需要统一修订入口。无需新增故事或业务数据迁移，不给未经测量的工期承诺。

未采用继续MySQL：用户明确要减少数据库安装配置。未采用仅增加H2而保留MySQL验收：仍需组员配置MySQL，不能达到简化目的。无需推倒业务需求或回滚已完成代码，目前没有业务实现。

## 4. 具体修改清单（批准后应用）

### PRD：§2–3、§5–6、§8

- 旧：约30人业务系统及“并发事件按系统成功记录的顺序”验收。
- 新：本地课程演示范围，按顺序执行已确认业务流程；并发处理、多实例和线上部署不列为验收目标。30名成员仍可作为业务背景，不能写成30用户同时运行测试通过。
- 旧 NFR-001：同卡30次并发分配、交错事件与旧事件重放。
- 新 NFR-001：顺序演示中同卡最多一个当前名额；归还或撤销后合法队首获配；重复操作旧名额不影响后继。以记录、页面和实际顺序操作证据验收，不开展并发测试。
- NFR-002权限及NFR-003操作记录保留可测试条款；NFR-003保留成功操作字段核查，失败回滚用代表性测试，不再要求每类干预都故障注入。
- R01改为普通一致性风险“重复归还或旧页面操作误改下一名额”，用独立名额ID及状态检查处理。现有课程材料中的“并发或一致性风险点”以此一致性例子说明，不虚构并发验证或代替老师确认课程原文。
- AC-010-4、AC-012-3–4的业务结果保留，测试方式改为依次执行两种顺序，不构造竞争事务。

### 架构与ADR

- 旧 AD-2 / ADR-002：MySQL InnoDB、READ COMMITTED、固定GPU行锁、跨卡升序取锁。
- 新：H2本地持久化、普通应用事务、当前名额唯一约束和状态校验；取消专门行锁协议及不同卡并行要求。
- 旧 AD-3 / ADR-003：allocation_id和通用command_id幂等结果存储、并发同键回滚再读取。
- 新：保留每轮新allocation_id和已结束状态检查；重复开始/归还/审核返回已处理；删除通用command_id存储及重试协议，释放仅针对原名额。
- 旧 AD-4 / ADR-004：同锁、数据库UTC微秒时间、transition_seq决定提交顺序。
- 新：处理时读取当前状态和期限，续期先处理则后续到期按新期限判断；释放先处理则旧续期失效。采用可注入UTC时钟支持边界测试，不维护每卡提交序号。不缩短期限、不复活已结束名额，D039的24小时分支保留。
- 旧 AD-5：锁超时、死锁及有界重试、命令结果和消息去重矩阵。
- 新：普通事务保存业务与必需消息/记录，失败回滚；状态无变化不重复产生结果通知，不建设命令重试基础设施。
- AD-6保留简单到期检查与启动补查，AD-7保留当前等待项调序的业务含义；调序规则中用于重放的操作顺序用普通操作记录ID，不再依赖每卡transition_seq；本次不额外改变锚点移动算法。
- AD-8改为本机HTTP演示，保留Session/CSRF/角色/归属；删除正式HTTPS部署及分库受限MySQL账号要求。
- 时间列从MySQL特定DATETIME(6)改为H2支持的UTC时间存储并写清Java映射，API带Z、页面上海时区不变。AD/ADR原编号保留并注明新决定取代的部分，不擦除真实旧决策。

### 验证计划

- 旧：真实MySQL、多独立连接、30连接屏障、不同卡并行、强制竞争、锁等待3秒及额外重试2次。
- 新：H2独立测试文件；顺序验证登录、申请、队列、分配、开始、归还、管理员操作、消息和重启。保留重复归还/旧名额、续期前后处理顺序、6→12/24/30小时边界和代表性失败回滚。
- 旧：正式HTTPS、每日自动备份、恢复前阻断检查及监控计数。
- 新：本地HTTP、停止应用后手动备份数据文件、在独立副本还原并核对关键记录后演示重启。恢复演示不覆盖原文件；不把普通文件复制描述成运行中的一致性备份。

### epics.md、配套SPEC及命令契约

- Story1.1的版本验收由“MySQL服务端版本”改为“H2实际依赖版本与文件路径”；分库账号改为隔离的数据目录和测试临时库。
- Story1.2、2.1–2.8、3.1–3.7中全部同时提交/多管理员/多连接验收改为对应顺序功能或重复操作检查；删除命令键指纹/回放结果、锁后、死锁重试、transition_seq等技术依赖。仍有效但状态已经变化的管理员确认可以用简单所见状态核验，不强制引入通用版本协议。
- Story3.8按本地启动与持久化恢复验收重写，保留故事ID；Story3.9仍记录真实BMAD过程，实验A不因技术简化被视为已完成。
- 同步SPEC.md及account-provisioning.md、lifecycle-commands.md、inbox-behavior.md、priority-commands.md，移除与新范围矛盾的并发/命令键规则。保留所有业务权限、理由、旧名额隔离、当前项调序、首次已读事实和通知归属规则。
- 历史story-proposals和审阅/收尾文件保留并标注仅作历史；下游以修订后的epics和SPEC为准，不把旧候选或阶段报告作为另一套现行契约。

### 入口、实现规格及跟踪

## 5. 交接与完成标准

范围分类：中等设计调整，不重排三个史诗和20条故事；由当前/下一位开发agent接续修改，人员不预分工。

批准后先统一现行契约及引用，再审阅简化后的Story1.1规格并开始工程初始化；不先实现一套与现行文档冲突的代码。本次不自动推送GitHub，是否提交按用户后续指令处理。

完成标准：

1. 现行入口不再要求安装MySQL、30连接并发或复杂锁协议；旧要求作为历史能追溯。
2. 全部故事及NFR以新的可执行验收为准，需求编号不重排；H2版本和准确启动命令在真实实现时验证。
3. 组员拉取后按文档在本机初始化数据文件，能够演示完整业务闭环并重启保留记录；测试和数据库文件不入Git。
4. BMAD规格、冲刺、实现、审阅、测试和交接记录能相互追溯；尚未实现/验证的事项保持未完成状态。
