# Epic 2 Context: 成员完成普通申请、获配、使用与归还闭环

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让成员通过网页完成指定 GPU 的普通申请、按卡等待、部分获配、确认开始与归还，随后由合法队首接续使用；系统处理短时未开始、24 小时异常和已开始逾期，管理员核实后可释放。成员能查看本人状态、公开队列及站内消息，形成无需后续高级干预功能即可演示的普通使用闭环。

## Stories

- Story 2.1: 成员提交指定 GPU 普通申请并查看受理结果
- Story 2.2: 按卡分配普通申请并查看本人名额
- Story 2.3: 成员按卡确认开始使用
- Story 2.4: 成员按卡确认完成并归还名额
- Story 2.5: 自动处理到期与未开始异常
- Story 2.6: 管理员核实异常或逾期后释放名额
- Story 2.7: 成员查看各 GPU 的公开等待队列
- Story 2.8: 成员查看站内消息并标记已读

## Requirements & Constraints

- 普通申请免审批，首次预计时长为 1–72 整数小时。多卡申请按指定 GPU 建立独立等待项；有意重复同卡申请保留，不合并、不因同人额外加减优先级。
- 每卡独立分配和计时，允许部分获配；忙碌卡的队首不能阻塞不冲突的卡。部分获配不改变其余项的原提交时间及接收顺序；整单状态从按卡关系推导。
- 查询和分配共用排序策略、评价时间。依次为等待严格超过 72 小时、已批准紧急及其余项，各组按原提交时间、接收序号排序。本史诗先交付普通流程，高级优先级入口随后增加。
- 每张卡最多一个当前有效名额，异常和逾期仍占名额。每轮使用新 allocation_id，旧开始、归还、到期或撤销不能恢复旧名额或改变后继，即使两轮属于同一成员。
- 确认开始不重置期限。未开始且批准总跨度不足 24 小时，到期释放；跨度达到 24 小时，原分配满 24 小时未开始则标异常保留。已开始到期标逾期保留。归还立即释放；核实异常须确认可释放，核实逾期须确认任务完成。
- 系统只记录使用权和人工声明，不连接服务器、探测任务、执行训练或终止进程；名额状态不能代表硬件真实占用。

## Technical Decisions

- 使用单实例 Vue 3、Spring Boot 3.3.13、Java 21 与 H2 文件库，按顺序操作验收；不恢复历史 MySQL、并发专项或复杂命令幂等协议。版本化迁移先于应用启动，测试使用独立临时文件库，数据文件与凭据不入 Git。
- 所有名额写入通过同一应用服务，页面和后台扫描不直接写表。结束原名额、更新映射、合法后继获配及必需审计消息同事务；必需写入失败整体回滚，提交成功后才报告成功。
- 当前映射以 GPU 唯一，allocation_id 唯一且外键对应同卡历史；映射是有效性唯一权威。历史只追加，原分配、开始、异常和首次结束事实保持。
- 使用可注入 UTC 时钟，H2 保存带时区时刻，API 时间带 Z、标识为字符串，页面显示 Asia/Shanghai。每 60 秒扫描并启动补查，到期、24 小时未开始及空闲有等待项均按当前记录重新判断。
- 后端验证 Session、角色、本人归属和 CSRF。公开队列仅姓名与顺序，不能带出申请、账号、名额、消息或审计详情。无变化不重复产生审计、通知或后继；延期后新一轮逾期可产生新通知。

## UX & Interaction Patterns

- 本人页面按卡展示等待、获配和历史，明确提交受理与真正获配的区别；单卡开始和归还不连带其他卡。
- 加载、空态和失败可区分；失败不伪装为空列表或成功。管理核实要求理由及确认，仍有效但所见状态变化时返回冲突并刷新核实。
- 站内消息按本人归属展示。明确点击后才保存单条首次已读时间，查询不自动标记；历史消息不反向改变业务状态。

## Cross-Story Dependencies

- 依赖已完成的账号、Session 和固定 GPU 目录。按提交入队、分配、开始、归还、到期和核实顺序增量交付；队列与收件箱复用已有策略及消息来源。
- 每条故事仅建立其所需结构，不预建续期或高级干预表；未交付入口不作为当前验收前置。紧急审核、人工调序、续期、直接延期、代归还与主动撤销由后续史诗扩展并回归。
- 保存实际运行及静态检查的区别、证据和交接记录。实验 A 须在选定 X/Y 故事实现前准备，普通开发不能冒充干净会话对照。
